代码风格与设计范式
====================

本文档总结 `NanoLiveLens` 代码库当前稳定出现的编码范式、工程风格与常见设计习惯。

目标不是定义一套脱离现状的“理想规范”，而是尽量准确地描述当前代码已经形成的习惯，并为后续修改提供一致的参考。


整体特征
--------

本代码库的风格不是单一流派，而是以下几种倾向的组合：

- 现代 C++：使用 `C++23`、`concept`、`requires`、移动语义、`std::optional`、`std::jthread`、`std::println` 等语言与标准库特性。
- 工程务实：接受宏、全局状态、轻量运行时多态，只要它们能显著改善调用体验或工程可维护性。
- 自建基础设施：对第三方库通常不直接裸用，而是先做一层项目内包装，再以统一语义暴露给业务代码。
- 运行时装配：业务代码通常只关心“能力”或“接口语义”，而非底层容器、平台或第三方实现的具体类型。


核心设计范式
------------

RAII 不只管理资源
~~~~~~~~~~~~~~~~~

本项目中的 `RAII` 不仅用于文件、对象、指针等传统资源，还被用于表达“某种状态在某个作用域内成立”。

典型例子是容器租约：

- `ContainerLease`
- `AssoContainerLease`

它们表达的不是“拥有容器”，而是：

- 构造时，将某个对象或键值对注册到容器中
- 析构时，将同一对象或键值对从容器中移除

这种模式适用于注册回调、挂接活动对象、临时加入索引或集合等场景。后续设计新组件时，凡是存在“进入作用域注册，离开作用域注销”的模式，应优先考虑用 `RAII` 封装，而不是让调用者手动成对调用。


以能力为中心，而非以具体类型为中心
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

代码库中常见如下设计思路：

- 不直接要求某个具体容器类型
- 先定义“对象需要具备哪些操作”
- 再通过模板约束或轻量接口包装接入具体实现

例如：

- `AddandremoveableContainer`
- `AddandremoveableAssoContainer`

这类 `concept` 的作用是描述“可承载什么行为”，而不是绑定某一种标准容器。这种思路应继续保持，尤其是在基础设施层中，尽量优先表达能力边界，而不是把抽象收缩到具体实现名。


编译期约束与运行时多态并用
~~~~~~~~~~~~~~~~~~~~~~~~~~

本项目不是纯模板式设计，也不是纯虚接口式设计，而是混合使用两者：

- 用 `concept` / `requires` 在编译期过滤非法用法
- 用接口类和类型擦除在运行时保留动态绑定能力

例如容器租约相关实现中：

- 编译期约束容器是否满足插入、迭代、删除能力
- 运行时通过 `IAddandremoveableContainerRef` / `IAddandremoveableAssoContainerRef` 擦除具体容器类型

这种混合方式是本项目很鲜明的风格。它的目标不是追求语言纯度，而是同时获得：

- 编译期防错
- 运行时灵活绑定
- 业务层较低的耦合度


自建薄封装
~~~~~~~~~~

项目大量使用轻量辅助层统一第三方库和标准库的使用方式，例如：

- `Box` / `Rc` / `Weak`
- `newBox` / `newRc`
- `UNWRAP`
- `LIFETIMEBOUND`
- `SafeElementInstancer`

这说明项目倾向于通过薄封装建立一致的使用语义，而不是让各处代码直接面对原始 API。新增基础设施时，应优先考虑：

- 是否能沿用已有薄封装
- 是否有必要以相同风格新增一层统一接口

但也应克制无收益的包装，避免形成过深的抽象叠加。


命名风格
--------

类型与接口
~~~~~~~~~~

类型名和接口名通常采用 PascalCase，例如：

- `RmlUIElement`
- `ContainerLease`
- `SafeElementInstancer`
- `AppState`

接口类常使用 `I` 前缀，例如：

- `IAddandremoveableContainerRef`
- `IAddandremoveableAssoContainerRef`

这类命名在项目中已形成稳定习惯，应保持一致。


函数与方法
~~~~~~~~~~

函数命名总体偏向直接、语义化，但不强制单一风格。常见形式包括：

- `setupAllJsBinding`
- `bindEventHandlers`
- `processDefaultAction`
- `getAppState`
- `initAfterConstruct`

建议延续当前风格：

- 业务动作使用动词短语
- 获取器使用 `get*`
- 初始化逻辑使用 `init*`
- 注册逻辑使用 `reg*` 或 `register*`


成员变量
~~~~~~~~

成员变量通常使用尾随下划线，例如：

- `isDragging_`
- `mousePosWhenBeginDrag_`

但部分较早或较简单的成员可能未使用尾随下划线，例如：

- `firstInited`
- `isWindowElement`

建议新代码优先使用尾随下划线，以避免与参数名、局部变量名冲突。


局部变量
~~~~~~~~

局部变量倾向简洁直观，例如：

- `ctx`
- `rt`
- `winMan`
- `script`
- `children`

项目不追求极长的“全拼式企业命名”，更重视上下文下的可读性。对于作用域较小、语义明确的变量，短名是可接受的。


所有权与生命周期
----------------

显式表达所有权
~~~~~~~~~~~~~~

代码库对所有权和生命周期较为敏感，常见做法包括：

- 用 `Box` 表达独占所有权
- 用 `Rc` / `Weak` 表达共享关系
- 用 `gsl::not_null` 限制不可为空指针
- 用 `LIFETIMEBOUND` 标注引用或指针与外部对象的生命周期关系

这说明本项目倾向于把生命周期关系显式编码进类型层。新增接口时，如果存在明显的所有权规则，应该优先通过类型而不是注释表达。


允许全局状态，但应控制边界
~~~~~~~~~~~~~~~~~~~~~~~~~~

项目并不排斥全局状态，例如 `AppState`。这说明设计取向是务实的：在 UI、脚本、窗口管理等强关联模块之间，接受集中式状态入口，以换取调用便利和上下文统一。

但这种模式应尽量满足两个要求：

- 全局状态结构本身清晰、字段职责明确
- 业务代码通过少量固定入口访问，而不是散落大量隐式全局依赖


宏的使用态度
------------

本项目接受少量语义型宏，例如：

- `UNWRAP`
- `EXCEPT`
- `newBox`
- `newRc`

这表明代码风格不是“严格禁宏”，而是允许宏承担以下职责：

- 统一样板写法
- 强化断言语义
- 提高调用简洁性

但宏的使用应保持克制。新增宏时应优先确认：

- 是否确实比函数模板更合适
- 是否不会隐藏副作用
- 是否不会让调试和阅读成本明显升高


错误处理与调试风格
------------------

断言优先，日志直接
~~~~~~~~~~~~~~~~~~

项目倾向在开发期直接暴露问题，而不是过早追求复杂容错。常见手段包括：

- `assert`
- `UNWRAP`
- 直接输出异常和调试信息

同时，大量使用：

- `std::println`
- `std::cerr`

这说明调试体验在本项目中很重要。后续新增基础设施时，应尽量保留“出错时现场可见”的特点，而不是将错误静默吞掉。


对第三方库进行防护性包装
~~~~~~~~~~~~~~~~~~~~~~~~

例如 `SafeElementInstancer` 会捕获元素构造时的异常并返回安全占位对象。这体现了一个明确倾向：

- 可以让第三方库继续工作
- 但不应让外部异常直接穿透第三方内部调用栈

类似场景下，应优先考虑“在边界层吸收异常并记录上下文”，而不是把第三方库暴露为无防护接口。


测试风格
--------

偏行为驱动的可运行测试
~~~~~~~~~~~~~~~~~~~~~~

项目中的测试并不总是采用纯断言、纯最小单元的形式。部分测试更像一个小型运行程序：

- 启动本地服务
- 发送请求或消息
- 驱动事件循环
- 输出中间状态
- 最后给出通过/失败结论

这种风格尤其适合集成行为、异步交互、脚本绑定、UI 联动等不易抽成纯函数的场景。

因此，在为此类模块写测试时，可以接受：

- 适度的日志输出
- 明确的测试流程段落
- 对移动语义、生命周期和回调行为的端到端验证


代码组织与模块边界
------------------

头文件与实现文件分离
~~~~~~~~~~~~~~~~~~~~

项目大量采用 `.hxx` / `.cxx` 配对组织方式，并区分：

- `public`
- `private`
- `subprojects`
- `vendor`

这是一种较传统但清晰的 C++ 工程布局。新增模块时，应优先保持现有结构，而不是混入风格差异很大的目录组织方式。


基础设施优先收敛在公共层
~~~~~~~~~~~~~~~~~~~~~~~~

与容器、内存、生命周期、安全性相关的通用工具，倾向放在 `EatiEssentials` 一类公共层中。  
业务代码则更多聚焦：

- UI 行为
- 脚本绑定
- 窗口逻辑
- 应用状态协作

因此，新增工具时应先判断它属于：

- 通用基础设施
- 某个子系统的局部辅助

不要把明显通用的机制散落到业务文件中。


格式与编码
----------

项目已经明确约定以下基础格式：

- 编码：`UTF-8`
- 换行：`CRLF`
- 缩进：制表符
- 文档注释：支持 Doxygen 风格

同时，构建系统为 MSVC 显式开启 `/utf-8`。这意味着：

- 文本编码不是附属问题，而是工程一致性要求的一部分
- 读写文件、补充文档、处理中文文本时，应显式保证 UTF-8


推荐延续的实践
--------------

- 对生命周期敏感的行为，优先考虑 `RAII`
- 对抽象边界，优先表达“能力”而非“具体实现类型”
- 对第三方库，优先先包一层再进入业务代码
- 对所有权关系，优先让类型系统表达，而不是靠约定
- 对调试和异常，优先保证“能看见、能定位”
- 对新代码，优先贴近现有命名、缩进和注释习惯


需要警惕的风险
--------------

- 过多轻量包装可能演化为难以追踪的抽象叠加
- 宏若继续扩张，可能削弱可读性和工具友好性
- 全局状态若无边界，可能逐渐抬高模块耦合
- 类型擦除若层次过多，可能让调用语义变得隐蔽
- 中文与英文命名、注释混用若缺乏约束，可能导致风格漂移

因此，后续演进的目标不应是抹掉当前风格，而应是：

- 保留其工程务实与抽象灵活的优点
- 压制无节制增长的包装层、宏和隐式耦合


总结
----

`NanoLiveLens` 的代码风格可以概括为：

- 现代 C++，但不教条
- 注重生命周期与所有权表达
- 用编译期约束和运行时多态共同塑造抽象边界
- 大量依赖自建薄封装统一项目语义
- 接受务实的全局状态与工程性妥协，但强调可见性和一致性

后续新增代码时，最重要的不是追求某种外部“标准答案”，而是保持与这些既有范式一致，让代码继续表现为同一个项目，而不是多个风格互相拼接的集合。
