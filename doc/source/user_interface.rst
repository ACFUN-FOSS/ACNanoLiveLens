用户界面
========

本文档说明当前项目中「用户界面资源」的分类方式，以及不同分类下允许使用的 C++ 访问策略。


背景
----

当前项目的界面由以下几部分共同构成：

- `rml`
- `rcss`
- 绑定这些界面结构的 C++ 代码

这些界面资源并不都是同一种性质。

有些界面是程序内部契约的一部分，结构必须稳定，程序也明确依赖其固定元素存在。  
另一些界面则允许用户修改，此时程序不能把界面结构当成绝对可信输入。

因此，当前项目将所有界面分成两类：

- `factory`
- `user`


factory 界面
------------

`factory` 的含义是：

- 界面资源由程序原厂提供
- 用户不应修改
- 程序必须基于这套原厂 `rml / rcss` 才能正常运行

这类界面的特点是：

- 界面结构是程序内部协议的一部分
- C++ 代码可以明确依赖某些元素一定存在
- 如果元素缺失，说明资源包或程序本身已经损坏

因此，对 `factory` 界面允许使用「强契约」访问方式，例如：

- `requireFactoryElement(...)`
- `UNWRAP(findChildOrSelfById(...))`

这里的设计目标不是容错，而是尽快暴露程序资源缺陷。


当前属于 factory 的界面
~~~~~~~~~~~~~~~~~~~~~~~

目前约定以下界面属于 `factory`：

- `login_win`
- `msg_box`


user 界面
---------

`user` 的含义是：

- 界面资源允许用户自定义
- 程序仍然假设这些界面应该包含某些关键元素
- 但如果用户提供的 `rml` 存在问题，程序必须继续运行并报告错误，而不是崩溃

这类界面的特点是：

- 界面资源属于用户输入的一部分
- 结构不可信
- 程序应当采用“可恢复”的错误处理方式

因此，对 `user` 界面不应使用「缺元素直接断言崩溃」的访问方式。  
更合适的方式包括：

- `requireUserElement(...)`
- `ElementDynRef`
- 返回空指针或异常、由上层捕获并报告的查询接口

这里的设计目标是：

- 允许局部功能失效
- 允许记录错误
- 但主程序应继续运行


当前属于 user 的界面
~~~~~~~~~~~~~~~~~~~~

目前约定以下界面属于 `user`：

- `winframe`
- `danmaku_monitor`
- `danmaku_item`


两类界面的代码策略
------------------

当前建议的访问策略如下。


factory 代码
~~~~~~~~~~~~

`factory` 界面的 C++ 代码可以：

- 假设关键元素必然存在
- 使用强约束 API
- 在资源破坏时快速失败

推荐接口：

- `requireFactoryElement(...)`

其语义是：

- 返回引用
- 一定不为空
- 找不到时直接触发 `assert`

这适合「程序资源损坏属于开发或分发错误」的场景。


user 代码
~~~~~~~~~

`user` 界面的 C++ 代码应当：

- 把界面结构问题当成可报告、可恢复错误
- 不允许因为界面缺少元素而直接终止程序

推荐接口：

- `requireUserElement(...)`
- `ElementDynRef`

其中 `requireUserElement(...)` 的语义是：

- 返回引用
- 一定不为空
- 找不到时抛异常

这样错误可以被更高层捕获并转化为：

- 日志
- UI 错误提示
- 局部功能禁用

而不是直接崩溃。


为什么要显式区分
----------------

如果不显式区分 `factory` 和 `user`，代码很容易退化成两种坏情况之一：

- 对所有界面都过度防御，导致原厂界面契约被弱化，错误暴露过晚
- 对所有界面都直接断言，导致用户自定义资源一出错就崩溃

这两种结果都不好。

因此，本项目选择：

- 对 `factory` 使用强契约
- 对 `user` 使用可恢复契约

这不是「一个接口风格问题」，而是界面资源所有权和可信度不同所决定的工程策略。


接口约定
--------

当前约定以下接口语义：

- `requireFactoryElement(...)`
  - 返回 `Rml::Element &`
  - 找不到时直接 `assert`

- `requireUserElement(...)`
  - 返回 `Rml::Element &`
  - 找不到时抛 `ElementNotFoundErr`

- `ElementDynRef`
  - 适合反复按查询表达式重新解析用户界面元素
  - 找不到时抛 `InvalidElementDynRefErr`


迁移建议
--------

后续整理界面代码时，建议按下面的方向逐步收敛：

- `login_win`、`msg_box` 这类 `factory` 界面，优先改成 `requireFactoryElement(...)`
- `winframe`、`danmaku_monitor`、`danmaku_item` 这类 `user` 界面，优先改成 `requireUserElement(...)` 或 `ElementDynRef`
- 避免继续新增语义模糊的「既可能崩也可能恢复」的中间写法


总结
----

当前项目对界面资源的核心判断是：

- `factory`：资源是程序内部契约，允许强失败
- `user`：资源是用户输入，必须可恢复

一旦这个边界清晰，C++ 侧的元素访问策略也就应当随之明确分层，而不再混用。
